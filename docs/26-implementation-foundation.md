# 26. Implementation Foundation Plan

Статус: в работе. Основание: `docs/13-architecture.md` (monorepo, modular monolith),
`docs/24-multi-agent-plan.md` (contracts-first, merge order).

## Что уже создано

### Монорепо

| Путь | Назначение |
| --- | --- |

| `packages/contracts` | доменные enum'ы, коды ошибок, транспортные примитивы |

### Backend: модули

Создан скелет всех 13 модулей из `docs/13-architecture.md`:
auth, identity, athletes, club-structure, groups, scheduling, attendance,
finance, freezes, news, chat, analytics, audit.

Плюс инфраструктурные модули:

- `AppConfigModule` — валидация окружения на старте;
- `PrismaModule` — единственный экземпляр PrismaClient;
- `RedisModule` — клиент Redis (rate limiting auth, кэш/очереди); readiness
  проверяет Redis, если задан `REDIS_URL`;
- `HealthModule` — `GET /api/v1/health` (liveness) и `GET /api/v1/health/ready` (readiness).

Реализовано (issue A6 — инфраструктура аудита):

- `AuditModule` — глобальный модуль аудита по BR-007;
- `AuditService.record(event, tx?)` — запись события, в том числе внутри
  транзакции вызывающего модуля, чтобы аудит не расходился с данными;
- `AuditService.recordSafely` — запись, сбой которой не отменяет основное
  действие (например, фиксация неудачной попытки входа);
- `AuditService.list` — история изменений сущности для карточки в админке;
- `RequestContextService` (AsyncLocalStorage) + `AuditContextInterceptor` —
  автоподстановка `requestId`, IP и user-agent;
- словарь `AuditAction` и `AuditEntityType` в `packages/contracts` — общий
  контракт backend и админки.

Реализовано (issue B1 — слой identity):

- `IdentityRepository` (абстрактный класс как DI-токен) + `PrismaIdentityRepository`
  — доступ к `User`, `UserPermission`, `UserAthlete`, `GroupMembership`;
- `IdentityService` — профиль, связанные спортсмены, проверка ресурсного scope
  (`canAccessAthlete`);
- `GET /api/v1/me` — профиль и эффективные права; `GET /api/v1/me/athletes` —
  связанные спортсмены (ADR-0007);
- `resolvePermissions` и `canAccessAthlete` — чистые функции в
  `packages/contracts/src/identity.ts`, общие для backend и тестов;
- `StubAuthGuard` — временная заглушка аутентификации, включается только
  `LOCAL_AUTH_STUB=true`; без нее защищенные маршруты отвечают 401. Удаляется в B2.

Реализовано (issue B2 — аутентификация):

- `PasswordService` — Argon2id в PHC-формате (`@node-rs/argon2`, ADR-0004);
  хеш чужого формата считается несовпадением, а не ошибкой сервера;
- `TokenService` + `AccessTokenVerifier` + `AuthGuard` — access-токены (JWT,
  HS256) и защита маршрутов через `Authorization: Bearer`;
- `RefreshTokenService` — refresh-токены с ротацией: в БД хранится только
  SHA-256-хеш; повторное использование отозванного токена отзывает все токены
  пользователя;
- `RateLimiterService` — фиксированное окно на Redis (`INCR` + `EXPIRE`),
  лимиты по IP и по email отдельно;
- `AuthService` и эндпоинты `POST /auth/login`, `POST /auth/refresh`,
  `POST /auth/logout`;
- `TokenModule` — глобальный модуль проверки токенов: guard нужен всем
  доменным модулям, а зависимость от модуля auth создала бы цикл
  auth -> identity -> auth;
- `prisma/seed.ts` переведен на Argon2id: иначе созданный seed-ом суперадмин не
  смог бы войти.

Реализовано (issue B3 — приглашения):

- `InviteService` и `InviteRepository`: приглашение создается администратором с
  правом `users.manage`; в БД хранится только SHA-256-хеш токена, сам токен
  возвращается один раз при создании (провайдер доставки письма не выбран,
  docs/25-open-questions.md);
- перевыпуск гасит предыдущие неиспользованные приглашения;
- гашение приглашения атомарно (`consume`): при одновременных запросах успевает
  только один, второй получает `INVITE_ALREADY_USED`;
- проверки при принятии: срок действия, совпадение email, признак
  использования; роль берется из приглашения, а не из запроса;
- `PermissionsGuard` + `@RequirePermissions` — проверка прав на маршруте.
  Права вычисляются на каждом запросе через IdentityService (ADR-0006), поэтому
  отзыв права действует сразу; неаутентифицированный запрос получает 401, а не
  403;
- эндпоинты `POST /users/invites`, `GET /users/invites`,
  `POST /auth/accept-invite` (с лимитом попыток по IP: токен — секрет).

Реализовано (issues B5/B6 — индивидуальные права и ресурсный scope):

- `PermissionGrantService` — выдача и отзыв индивидуальных прав;
  `GET/POST /users/{id}/permissions`, `DELETE /users/{id}/permissions/{code}`
  под правом `permissions.manage`;
- истекшая выдача не действует: фильтр «бессрочная или с непрошедшим сроком»
  применяется при каждом чтении, иначе временный доступ остался бы навсегда;
- право, которое уже обеспечивает роль, нельзя ни выдать, ни отозвать
  (`PERMISSION_GRANTED_BY_ROLE` / `PERMISSION_IS_ROLE_BASED`): роль остается
  предсказуемой, а выдача не создает иллюзию управляемого доступа;
- изменения прав пишутся в audit log (BR-007), финансовые выдачи
  дополнительно отмечаются в логах (BR-010);
- `ResourceScopeService` — вторая половина правила из
  `docs/21-permission-matrix.md`: наличие permission не дает доступа к чужой
  группе или спортсмену. Методы `checkAthlete`, `checkGroup`,
  `assertAthleteAccess`, `assertGroupAccess`, `visibleGroupIds`;
- `canAccessAthlete` и `canAccessGroup` возвращают решение с причиной
  (`ScopeDecision`), а не boolean: причину видно в логах и проверяют тесты;
- модуль identity экспортирует `ResourceScopeService`: доменные модули обязаны
  проверять scope отдельно от прав.

Реализовано (эпик C, часть 1: C1–C5):

- `ClubStructureService` — филиалы, залы, тренеры; изменения под правами
  `branches.view` / `branches.manage`, аудит по BR-007, мягкое удаление через
  `archivedAt` (docs/08-database.md);
- вложенный маршрут `POST /branches/{id}/halls` использует отдельный DTO без
  `branchId`: ValidationPipe настроен с `forbidNonWhitelisted`, и лишнее поле
  из пути приводило бы к 400;
- `AthletesService` — карточки спортсменов и связи аккаунтов (C4–C5). Здесь
  scope не только проверяется, но и **влияет на выборку**: суперадмин и
  сотрудник с `scopeAllGroups` видят всех, тренер — спортсменов своих групп,
  участник — связанных (docs/21-permission-matrix.md, Enforcement);
- контакты (`phone`, `email`) скрываются без права `athletes.contacts.view`
  (docs/15-security.md, Privacy); заметки клуба не отдаются в `/me/athletes`;
- «основной» аккаунт спортсмена один: при `isPrimary: true` признак снимается
  с остальных связей.

Миграция `20260102000000_trainer_profile_optional_user`: `TrainerProfile.userId`
стал nullable. По `docs/04-roles-permissions.md` часть тренеров работает без
входа в систему, и обязательная связь с `User` заставляла бы заводить аккаунт
каждому. `@unique` сохранен: он означает «у одного аккаунта не более одного
профиля тренера», а тренеров без аккаунта может быть сколько угодно —
уникальный индекс Postgres считает NULL-значения различными.

Реализовано (эпик C, часть 2: C6–C8):

- `GroupsService` — группы, привязка филиалов (`GroupBranch`), назначение
  тренеров (`GroupTrainer`), состав (`GroupMembership`); права `groups.view` /
  `groups.edit`, аудит по BR-007;
- список групп ограничен scope: тренер видит только свои группы; пустой список
  видимых групп означает «ничего не видно», это не то же самое, что
  `null` («ограничений нет»);
- группа может заниматься в нескольких филиалах
  (`docs/00-project-overview.md`), «основной» филиал и «основной» тренер —
  по одному: при назначении нового признак снимается с остальных;
- назначения тренеров хранят историю: повторное назначение после снятия
  создает новую запись (`unassignedAt`), поэтому активный дубликат
  отклоняется;
- `GroupMembership` — история: завершение членства не удаляет запись, а
  проставляет `state = ENDED` и `leftAt`. Ограничение
  «одна активная группа на спортсмена» обеспечено частичным уникальным
  индексом, а сервис дает понятную ошибку с идентификатором текущей группы;
- `GET /groups/by-athlete/{athleteId}` — действующая группа спортсмена, нужна
  админке для перевода между группами.

Реализовано (эпик K, часть 1: web-админка):

- `apps/admin` — каркас Next.js 16 (App Router) + React 19 + Tailwind CSS 4,
  собирается в CI отдельным job;
- типы API генерируются из `openapi.yaml` (`openapi-typescript`), поэтому
  расхождение с backend видно на сборке, а не в рантайме; CI проверяет, что
  `schema.d.ts` не устарел;
- токены сессии лежат в `httpOnly`-cookie, а браузер обращается к backend через
  route handler `/api/proxy/...`. Это убирает CORS и не отдает токен
  JavaScript страницы (docs/15-security.md). Если access-токен истек, прокси
  обновляет его по refresh-токену и повторяет запрос один раз;
- экраны: вход, обзор (справочники и права пользователя), филиалы (список,
  создание, архивирование), группы и спортсмены (списки). Разделы, требующие
  не имеющихся прав, показываются только для чтения — окончательная проверка
  все равно на backend;
- проверка входа выполняется по HTTP скриптом `scripts/check-admin.mjs`: он
  разбирает скрытые поля формы server action и проверяет, что вход ставит
  `httpOnly`-cookie, защищенные страницы без сессии перенаправляют на вход, а
  прокси отдает данные backend от имени пользователя.

Реализовано (эпик K, часть 2: админка до полноты контракта):

- карточка группы: филиалы (привязка и отвязка), тренеры (назначение и снятие),
  состав (добавление и завершение членства), архивирование группы;
- карточка спортсмена: изменение контактов и статуса, связи аккаунтов
  (привязка, снятие, признак основного), архивирование;
- создание групп, спортсменов и филиалов прямо из списков;
- раздел пользователей: список с фильтрами и экран прав, где ролевые права и
  индивидуальные выдачи показаны раздельно. Отозвать можно только выданное
  лично: право роли отзывается сменой роли (ADR-0006), и смешивать их в
  интерфейсе нельзя — администратор искал бы кнопку там, где ее быть не должно;
- `GET /users` (новый эндпоинт): список с фильтрами и пагинацией. Доступен с
  правом `users.manage`, потому что отдельного права на просмотр в каталоге
  нет (`docs/04-roles-permissions.md`). Нужен, чтобы выдать право или связать
  аккаунт: без списка выбирать аккаунт не из чего;
- в ответ `GET /users/{id}/permissions` добавлены email и имя: экран прав
  открывается по идентификатору, а отдельного `GET /users/{id}` в контракте нет;
- админка не падает при недоступном backend: сетевые ошибки дают 503 в прокси и
  понятную страницу вместо технической ошибки Next.

Реализовано (инфраструктура):

- collation базы данных задана явно и одинаково во всех окружениях через ICU
  (ADR-0008). Причина: `ILIKE` для кириллицы зависит от collation, и при
  collation `C` (локальный `initdb --no-locale`) поиск по ФИО молча не работал
  бы, тогда как в CI работал.

Реализовано (эпик D, часть 1: фундамент расписания):

- контракт расписания: шаблон квартала со слотами, экземпляр занятия, перенос и
  отмена, фильтры списка занятий (`packages/contracts/src/schedule.ts`);
- коды ошибок расписания: конфликт занятия, занятость тренера и зала, попытка
  изменить опубликованный шаблон или прошедшее занятие;
- `club-calendar.ts` — календарные расчёты: границы кварталов, дни недели по
  ISO-8601, перевод локального времени клуба в UTC через `Intl`. Это тот слой,
  где ошибка была бы незаметной: арифметика через `Date.UTC` сдвигала бы
  занятие на час при смене летнего времени. Покрыт 23 тестами, включая переход
  на летнее время и занятия через полночь;
- решения по модели зафиксированы в ADR-0009.

Реализовано (эпик D, часть 2: расписание целиком на backend):

- шаблоны на квартал со слотами под `schedule.view` / `schedule.edit`: повторный
  шаблон на тот же квартал отклоняется, слоты внутри шаблона не пересекаются
  (занятие через полночь считается корректно);
- публикация требует хотя бы одного слота, после публикации слоты зафиксированы
  (`SCHEDULE_TEMPLATE_PUBLISHED`): расписание уже показано, занятия
  материализованы, дальше только точечные изменения;
- материализация занятий на будущие даты квартала: идемпотентна за счет
  уникальности `(groupId, startsAt)`, при `regenerate` удаляет только будущие
  занятия (прошедшее занятие — факт истории, его пересоздание стерло бы
  посещаемость);
- конфликты (тренер или зал заняты в другой группе) не пропускаются молча:
  ответ содержит конфликтующие даты. Иначе о накладке узнали бы родители;
- занятие наследует основной филиал группы и копирует зал и тренера из слота
  (ADR-0009), поэтому смена тренера в шаблоне не переписывает уже созданные
  занятия;
- точечный перенос и отмена требуют причины, прошедшее занятие изменить нельзя:
  расписание прошедших занятий — история.

Живая проверка расписания: `node scripts/check-scheduling.mjs` — 28 утверждений
на реальной БД, включая проверку, что все занятия попадают на среду в 18:00 по
времени клуба, и что перенос не меняет шаблон.

Реализовано (эпик D, часть 3: экраны расписания в админке):

- `/schedule` — список квартальных шаблонов с состоянием (черновик или
  опубликовано) и форма создания;
- `/schedule/{id}` — карточка расписания: слоты с залом и тренером,
  публикация, материализация занятий. В опубликованном шаблоне слоты
  зафиксированы, поэтому форма добавления намеренно скрыта: иначе
  администратор искал бы способ изменить то, что менять нельзя;
- `/schedule/sessions` — занятия с точечным переносом и отменой. Видно, какие
  занятия созданы из расписания, а какие изменены, и указана причина изменения;
- пересоздание занятий помечено явно: удаляются только будущие, иначе
  потерялась бы посещаемость.

Реализовано (эпик E: посещаемость):

- журнал занятия под `attendance.view`, отметки — под `attendance.edit`, оба
  дополняются проверкой scope: тренер отмечает только свои группы;
- **журнал строится по составу группы на дату занятия**, а не по текущему
  списку. Иначе спортсмену, зачисленному в середине квартала, приписали бы
  отсутствия за занятия, которых не было в его расписании, а выбывшему —
  отсутствия после ухода;
- отметка идемпотентна: повторная запись обновляет статус и автора, а не
  создает вторую. Тренер исправляет ошибку в журнале, а не «дописывает»
  посещение. Отметку можно снять, если спортсмена отметили по ошибке;
- отметка спортсмена, не числившегося в группе на дату занятия, отклоняется
  (`ATHLETE_NOT_IN_GROUP`): это защищает журнал от задним числом дописанных
  отсутствий;
- BR-008 разделен строго: `PlannedAbsence` — предупреждение родителя,
  `Attendance` — подтвержденный факт. Предупреждение не создает отметку,
  итог остается за тренером;
- сводка за период считает знаменатель по факту членства на каждую дату:
  зачисление позже остальных не занижает посещаемость задним числом;
- каждое изменение попадает в audit log: `attendance.marked` для новых отметок,
  `attendance.updated` для изменений, отдельные действия для предупреждений
  (BR-007).

Живая проверка посещаемости: `node scripts/check-attendance.mjs` — 17
утверждений на реальной БД. Проверено, в частности: спортсмен, зачисленный
после первого занятия, в его журнал не попал; повторная отметка не создала
дубль; отметка спортсмена вне состава отклонена; предупреждение родителя не
создало подтвержденную отметку; в сводке знаменатель у рано зачисленного
больше, чем у позднего.

Реализовано (эпик E, часть 2: экран посещаемости в админке):

- журнал занятия: состав группы на дату, отметки и предупреждения родителей;
- отметка в один клик: три кнопки («Был», «Нет», «Уваж.») вместо выпадающего
  списка. Тренер отмечает на занятии, часто одной рукой, и лишний выбор из
  списка замедляет работу; статус передается значением кнопки;
- предупреждения об отсутствии вынесены отдельным блоком с пояснением, что это
  слова родителя, а итог подтверждает тренер (BR-008). Смешивать их с отметками
  нельзя: тогда предупреждение читалось бы как факт;
- если на дату занятия в группе не было спортсменов, экран объясняет, что журнал
  строится по членству на дату, и предлагает проверить состав: пустой список
  иначе выглядит как ошибка.

Реализовано (эпик F: финансы и заморозки):

- расчетные периоды по календарным месяцам (BR-001) под `payments.view` /
  `payments.edit`. Права есть только у суперадмина: тренер финансов не видит
  (BR-010), и это проверено вживую;
- период создается при первом обращении: иначе администратор не увидел бы, что
  месяц не заведен, и не смог бы внести оплату;
- **статус периода не вводится руками**, а выводится из суммы оплат и ручной
  отметки. Иначе отметка «оплачено» расходилась бы с фактическими
  поступлениями. Ручная отметка «оплачен полностью» (BR-003) имеет приоритет:
  она ставится именно тогда, когда сумма в системе не совпадает с реальностью;
- сумма оплаты произвольная (BR-002): для спортсмена, пришедшего в середине
  месяца, она может быть любой;
- повторная отправка с ключом идемпотентности не создает вторую оплату; отмена
  оплаты удаляет запись и пересчитывает период, чтобы ошибка ввода не осталась
  в истории как факт поступления денег;
- задолженность (BR-004): должник — только если спортсмен активен, месяц не
  отмечен оплаченным, в месяце была тренировка его группы и он не в заморозке.
  Для не-должников причина возвращается явно: руководителю важно отличать
  решение (заморозка, отметка) от отсутствия данных;
- заморозки (BR-005) — в существующем модуле `freezes`: один открытый период на
  спортсмена, начало и завершение можно вносить задним числом. Модуль не слит с
  финансами, потому что это отдельный сценарий со своими правами; но
  задолженность их учитывает, поэтому FinanceModule получает FreezeRepository из
  FreezesModule.

Живая проверка финансов: `node scripts/check-finance.mjs` — 42 утверждения на
реальной БД: переход UNPAID → PARTIALLY_PAID → PAID, идемпотентность, возврат в
UNPAID после отмены оплат, ручная отметка и ее приоритет, заморозка и отказ во
второй заморозке, отказ при завершении раньше начала, а также возвраты целиком
(см. ниже).

Реализовано (ADR-0010: возврат денег):

- **возврат — транзакция с направлением, а не удаление поступления.** В
  `PaymentTransaction` добавлен `kind` (`PAYMENT`/`REFUND`), сумма всегда
  положительна. Отмена ошибочной оплаты (`DELETE /payments/{id}`) по-прежнему
  удаляет запись — там денег не было; возврат же фиксирует, что деньги
  поступили и ушли, и обе операции остаются в истории (BR-007);
- **зачтено = поступления − возвраты.** `MembershipPeriodView.paidAmount` стал
  нетто, рядом добавлен `refundedAmount`: без него «внесено 0 при возврате
  25 000» выглядело бы потерей данных. Обе величины пересчитываются вместе
  (`refreshPeriodTotals`), поэтому разойтись не могут;
- статус периода считается по нетто, поэтому **полный возврат возвращает период
  в `UNPAID`**, и спортсмен снова становится должником. Ручная отметка BR-003
  сохраняет приоритет;
- возврат можно привязать к поступлению (`refundedPaymentId`) или оформить без
  привязки: бывают корректировки периода, не относящиеся к одной операции.
  Лимиты: по привязанному поступлению — не больше его суммы, по периоду — не
  больше суммы поступлений (`REFUND_EXCEEDS_PAYMENT`); возврат по поступлению
  чужого периода отклоняется (`REFUND_PAYMENT_MISMATCH`);
- идемпотентность проверяется **раньше лимитов**: при повторной отправке той же
  формы возврат уже учтен в сумме периода, и проверка лимита отклонила бы
  повторное нажатие как «возврат больше, чем поступило»;
- поступление с возвратами удалить нельзя (`PAYMENT_HAS_REFUNDS`): возврат
  потерял бы основание. Сам возврат тоже не правится через «изменить оплату» —
  его отменяют и оформляют заново;
- эндпоинты `POST /membership-periods/{periodId}/refunds` и
  `DELETE /refunds/{refundId}` под `payments.edit` (BR-010);
- в админке возврат оформляется из строки поступления (сумма ограничена
  остатком) либо как корректировка периода; лента периода показывает оба
  направления, возвраты выделены и их можно отменить.

Живая проверка возвратов на реальной БД: частичный возврат дал нетто 15000 при
возвращенных 10000 и статус `PARTIALLY_PAID`; повтор с тем же ключом
идемпотентности не создал второй возврат; возврат больше оплаты, возврат по
периоду без поступлений и возврат по оплате другого периода отклонены; оплата с
возвратом не удаляется; полный возврат вернул период в `UNPAID`, и спортсмен
снова стал должником; отмена возврата вернула зачтенную сумму.

Реализовано (эпик F, часть 3: сводка руководителя, F8):

- `GET /finance/summary` — сводка за месяц под `payments.view` (BR-010):
  выручка, задолженность, число должников и активных спортсменов, разбивка по
  филиалам. `analytics.view` здесь недостаточно: в сводке суммы, а не
  обезличенные счетчики;
- **два разных знаменателя считаются осознанно, и это подписано в интерфейсе**:
  выручка — по датам движений («сколько денег прошло в этом месяце», включая
  оплаты за прошлые периоды), задолженность — по расчетному месяцу (BR-004: долг
  за сентябрь остается сентябрьским, даже если его закрыли в октябре). Смешивать
  их нельзя: иначе руководитель увидел бы «выручку», которой в кассе не было;
- выручка — нетто (поступления минус возвраты, ADR-0010), рядом отдаются обе
  составляющие: по одной выручке невозможно понять, почему она упала — оплат
  стало меньше или выросли возвраты;
- филиал определяется основным филиалом группы спортсмена. Спортсмен без группы
  или без филиала попадает в отдельную строку «Филиал не назначен»: приписать
  его суммы первому филиалу значило бы показать руководителю чужие деньги как
  свои. Филиалы без движения и без должников не возвращаются — пустые строки
  мешали бы сравнению;
- `periodsWithoutExpected` (`debtorsWithoutExpected`) вынесены отдельно: такому
  спортсмену долг посчитать нельзя, и «нет долга» здесь означает незаполненное
  ожидание, а не оплату;
- в админке `/finance` показывает выручку, задолженность, сравнение филиалов с
  масштабными полосками и должников; обзор (`/`) показывает выручку месяца,
  должников и недостачу, ссылаясь на ту же сводку.

Живая проверка сводки: `node scripts/check-finance.mjs` — выручка равна
поступлениям минус возвраты, оплата в группе филиала отнесена к этому филиалу,
пустые филиалы не возвращаются, спортсмены без филиала отделены, активные
спортсмены посчитаны. Экраны проверяет `node scripts/check-admin-finance.mjs`:
выручка, задолженность, пояснение про разные знаменатели и сравнение филиалов
есть на странице, обзор админки берет выручку из сводки.

Реализовано (эпик B3, часть 2: приглашения в админке):

- `/users/invites` — создание приглашения (email и роль) и список действующих.
  Доступ под `users.manage`: приглашение выдает доступ в систему, и отдельного
  права на просмотр приглашений в каталоге нет (docs/04-roles-permissions.md);
- **интерфейс не делает вид, что письмо ушло.** Провайдер доставки не выбран
  (docs/25-open-questions.md), поэтому после создания экран показывает ссылку с
  токеном, кнопку копирования и прямо говорит, что передать ее нужно вручную.
  Иначе администратор ждал бы письма, которого не будет;
- ссылка показывается один раз — в ответе на создание. В БД хранится только
  SHA-256-хеш токена, поэтому повторно получить его нельзя ни из списка, ни
  после перезагрузки; об этом сказано рядом со ссылкой. Если ссылка потеряна,
  приглашение выписывается заново, а предыдущее гасится (перевыпуск);
- срок действия берется из ответа API (`INVITE_TTL_HOURS` настраивается), а не
  пишется текстом «трое суток»: администратор видит фактическую дату, а
  приглашение, истекающее в ближайшие сутки, помечается;
- `/invite/{token}` — публичная страница принятия: показывает адрес, на который
  выдано приглашение, и дает задать пароль и профиль. Страница вне `AppShell`:
  это не раздел админки, и навигация по недоступным без входа разделам здесь была
  бы обманом;
- **`GET /auth/invites/{token}`** добавлен ради этой страницы: без него форма не
  знала бы адрес, и человек заполнял бы пароль, получая `INVITE_EMAIL_MISMATCH`
  без объяснения. Эндпоинт публичный (у приглашенного нет аккаунта) и отдает
  только адрес, роль и срок. Неизвестный, истекший и уже использованный токен
  неотличимы (`INVITE_INVALID`), чтобы перебором нельзя было выяснить, какие
  приглашения существуют; попытки ограничены по IP так же, как при принятии;
- email в форме принятия показан текстом, а не полем: приглашение выдано на
  конкретный адрес, и редактируемое поле создавало бы ложное ощущение, что его
  можно поменять. Роль берется из приглашения, а не из формы.

Живая проверка полного цикла (`node scripts/check-admin.mjs`, шаг 14): создание
приглашения (201, токен выдан), список без хеша токена, экран с формой и
предупреждением о ручной доставке, просмотр по ссылке **без сессии** (адрес
совпадает, хеш не раскрыт), страница принятия без сессии, принятие (200, роль
STAFF), **вход приглашенного** (200, 7 прав роли), повторное принятие (409
`INVITE_ALREADY_USED`), неизвестный токен (400 `INVITE_INVALID`) и повторное
приглашение занятого адреса (409 `EMAIL_ALREADY_EXISTS`).

Реализовано (эпик F, часть 2: экраны финансов в админке):

- `/finance` — сводка расчетного месяца: должники, ожидаемая сумма, внесенные
  должниками суммы, число активных спортсменов. Месяц выбирается GET-формой и
  попадает в адрес страницы, поэтому ссылку на конкретный месяц можно передать
  коллеге;
- `/finance/debtors` — должники и **освобожденные с причиной** (BR-004). Причина
  берется из ответа API, а не выводится из суммы: «в заморозке» или «отмечен
  оплаченным» — это решение клуба, а «в месяце не было занятий» — отсутствие
  данных, и смешивать их в одном флаге «не должник» нельзя;
- `/finance/athletes/{id}` — карточка спортсмена: двенадцать месяцев выбранного
  года, периоды с оплатами, внесение и изменение оплаты, отмена ошибочной
  оплаты, ожидаемая сумма и ручная отметка «оплачен полностью» (BR-002, BR-003).
  Месяц без периода не скрывается, а показан строкой «период не заведен» со
  ссылкой: период создается при первом обращении, и администратору нужно видеть,
  что месяц не заведен, а не пустоту;
- заморозки (BR-005) — раздел в карточке спортсмена и отдельный экран
  `/finance/freezes`: выбор спортсмена списком (запоминать UUID администратор не
  должен), открытие заморозки и завершение с датой. Пока заморозка открыта,
  вторая не предлагается: одна открытая заморозка на спортсмена — ограничение БД,
  и кнопка, которая заведомо получит 409, только путала бы;
- **статус периода нигде не выбирается руками**: он выведен из суммы оплат и
  ручной отметки. Селект «статус» позволил бы поставить «оплачено» без денег;
- форма оплаты отправляет ключ идемпотентности, созданный один раз при
  монтировании формы: повторная отправка (двойной клик, повторная отправка после
  перезагрузки) не создает вторую оплату. Даты и ключ подставляются после
  монтирования, а не при отрисовке: вычисленные на сервере и в браузере, они
  давали расхождение гидратации;
- разделы внутри карточки разделены по правам: оплаты — `payments.*`, заморозки
  — `freezes.*`. Пользователь с индивидуальной выдачей одного права видит
  подсказку «доступно только для просмотра» по второму, а не пустой экран;
- ссылка на раздел «Финансы» в навигации показывается только при наличии
  финансового права, но окончательная проверка остается на backend (BR-010):
  тренер получает 403 с объяснением, а не пустые суммы;
- код раздела разделен по смыслу: `page.tsx` (сводка), `debtors/`, `freezes/`,
  `athletes/[id]/` — страницы; `period-forms.tsx`, `payment-forms.tsx`,
  `freeze-forms.tsx` — формы; `finance-ui.tsx` — общая разметка и подписи
  статусов; `finance-shared.ts` — разбор сумм и дат; `actions.ts` — server
  actions. Слитный файл форм на 570 строк не прошел бы ревью.

Живая проверка экранов финансов: `node scripts/check-admin-finance.mjs` — 30
утверждений. Проверено, в частности: разделы без сессии перенаправляют на вход;
список должников показывает подготовленного спортсмена; **оплата, отправленная
формой админки, действительно попадает в БД** (12 000, статус PAID) и
отображается в карточке; заморозка с началом до первого числа месяца
освобождает от задолженности с причиной FROZEN, и эта причина видна в списке
должников; повторная заморозка не предлагается. Отдельно: заморозка с середины
месяца должником не делает, но и не освобождает — задолженность оценивается на
первое число, и это ограничение подписано прямо на экране.

Остальные модули backend — заготовки с указанием спецификации. Реализация
ведется отдельными issue по merge order из `docs/24-multi-agent-plan.md`.

## Контракт OpenAPI

`openapi.yaml` в корне — машинно-читаемый контракт между backend, админкой и
мобильным приложением (`docs/09-api.md`, `docs/23-api-contract-plan.md`).

Документированы реализованные разделы: health, auth, identity, invites,
permissions (11 маршрутов, 13 операций, 24 схемы, 5 переиспользуемых ответов).
Разделы athletes, groups, schedule, attendance, finance, news, chat, analytics
добавляются по мере реализации эпиков.

`scripts/validate-openapi.mjs` проверяет:

- YAML разбирается и соответствует OpenAPI 3.0.3;
- все `$ref` разрешаются, внешних ссылок нет;
- у каждой операции есть `operationId` (уникальный), `tags` и `responses`
  с описанием;
- **все маршруты, реализованные в приложении, присутствуют в контракте** —
  список ожидаемых маршрутов в скрипте обновляется вместе с новым эндпоинтом.

Последняя проверка — самая полезная: она не дает контракту молча отстать от
кода, что и произошло до этой задачи.

Ограничение, которое стоит знать: Swagger UI (`/api/v1/docs`) строится из
декораторов контроллеров и не читает этот файл. Схемы ответов в Swagger неполны,
поскольку контроллеры возвращают типы из `packages/contracts` без
`@ApiProperty`. Поэтому **источник истины для клиентов — `openapi.yaml`**, а
Swagger удобен для ручных проб. При добавлении эндпоинта нужно обновить:

1. `openapi.yaml`;
2. список `expectedRoutes` в `scripts/validate-openapi.mjs`;
3. при необходимости — `docs/09-api.md`.

## Непрерывная интеграция (A3)

`.github/workflows/ci.yml` на push и pull request: сервисы `postgres:16-alpine`
и `redis:7-alpine`, затем установка зависимостей, генерация Prisma Client,
миграция тестовой базы, lint, typecheck, unit-тесты, сборка и e2e.

Те же шаги на Linux/macOS выполняет `scripts/ci-verify.sh`; на Windows —
`scripts/verify.ps1`.

Проверено локально: миграции применяются к пустой базе, после чего e2e-тесты
проходят на этой базе. Штатный `prisma migrate deploy` (как в CI) в этой
рабочей среде недоступен — schema-engine запускается песочницей и падает с
`spawn EPERM`, поэтому SQL применялся через `scripts/apply-migration.mjs`;
схема при этом идентична.

## Архитектурные решения

Зафиксированы ADR:

- `docs/decisions/ADR-0004-password-hashing.md` — Argon2id с PHC-форматом.
  Реализуется в B2; временный scrypt в seed подлежит замене.
- `docs/decisions/ADR-0005-orm-prisma.md` — Prisma как ORM и миграции, явный
  `output` клиента, частичные индексы рядом с миграцией, `GroupBranch`.
  Отклонение от ERD v1: связь группы с филиалом через `GroupBranch`, а не
  `branchId`. Кандидат на обновление `docs/22-erd.md`.
- `docs/decisions/ADR-0006-permissions-model.md` — модель прав: базовый набор
  роли в коде (MEMBER без permissions, доступ по scope), каталог и
  индивидуальные выдачи в БД, scope отдельным измерением, финансы через
  `isFinancial`.
- `docs/decisions/ADR-0007-identity-profile-contract.md` — форма `GET /me`:
  профиль без связанных спортсменов, права как `codes` + `grants`, scope явным
  полем, чистые функции вычисления прав и проверки доступа к спортсмену.
- `docs/decisions/ADR-0008-database-collation.md` — collation задается через ICU
  одинаково локально, в compose и CI: от нее зависит `ILIKE` для кириллицы, и
  при collation `C` поиск по ФИО молча не работает.
- `docs/decisions/ADR-0009-schedule-model.md` — расписание: шаблон и экземпляр
  разделены, экземпляр копирует ссылки, публикация фиксирует шаблон,
  материализация идемпотентна, прошедшие занятия не редактируются.
- `docs/decisions/ADR-0010-refunds.md` — возврат денег: направление транзакции
  вместо удаления поступления, зачтено = поступления − возвраты, возврат
  привязывается к поступлению либо оформляется как корректировка периода,
  лимиты возврата, отдельная отмена возврата.

Открытые вопросы для ADR: нет.

Осознанно не оформляется ADR: выбор Biome вместо ESLint (инструмент, не
архитектура; причина описана в `docs/27-local-development.md`).

## Следующие шаги

1. **Пропорциональная заморозка** — заморозка освобождает от задолженности,
   только если накрывает **начало месяца**: оценка идет на первое число.
   Заморозка с середины месяца должником не делает, но и не уменьшает
   ожидаемую сумму. Нужно решение (пропорционально дням либо закрывать месяц
   при заморозке внутри него) — это изменение денежной логики, поэтому
   требуется ADR.
2. **Занятия вручную в админке** — API готов (`POST /training-sessions`), экрана
   backfill нет: занятие задним числом заводят через API. Экраны финансов
   сделаны (эпик F, часть 2).
3. **Доставка приглашения** — экран и публичная страница принятия сделаны,
   но письмо по-прежнему не отправляется: администратор передает ссылку вручную,
   и интерфейс об этом прямо говорит. Нужен выбор провайдера доставки
   (docs/25-open-questions.md) и, при желании, повторная отправка ссылки — сейчас
   потерянную ссылку можно только перевыпустить.
4. `apps/mobile` — каркас Flutter (требует установленного Flutter SDK).
5. Обновить `docs/22-erd.md` под `GroupBranch` (см. ADR-0005).
6. Scope по филиалам: сейчас `User.scopeAllGroups` — булев флаг. Отдельная
   таблица scope потребует нового ADR (см. ADR-0006, Consequences).
7. Отдельные права для тренеров и структуры клуба: сейчас изменение тренеров
   опирается на `branches.manage`, а список пользователей — на `users.manage`,
   потому что в `docs/04-roles-permissions.md` нет подходящих прав на чтение.
   Если появится роль администратора клуба — нужен ADR.
8. Повторяющиеся занятия вне квартала: сейчас `ScheduleTemplate` привязан к
   кварталу, поэтому «каникулярное расписание» на две недели выразить нечем.
9. Массовая отметка посещаемости: API принимает до 200 отметок за запрос, но
   интерфейса «отметить всех присутствующими» пока нет.
10. Сводка посещаемости в админке: эндпоинт `/attendance/summary` готов, экрана
    нет. Полезен руководителю, но это уже часть dashboard.
11. Динамика по месяцам: сводка отдает один месяц (выручка, задолженность,
    филиалы), сравнения с прошлым месяцем нет. Нужен либо параметр периода, либо
    отдельный эндпоинт с рядом месяцев — вопрос к dashboard, а не к финансам.

Закрыто: A3 (CI), B1–B6, эпик C (C1–C8), админка по реализованным модулям,
эпик D (D1–D4), эпик E (E1–E2), эпик F целиком (F1–F8; F5 — возвраты по
ADR-0010, F8 — сводка месяца с выручкой и сравнением филиалов), экраны финансов
в админке (I8, I9).

Точные отметки по пунктам плана — в `docs/19-backlog.md`, раздел «Статус
выполнения»: буквы в названиях коммитов не совпадают с пунктами плана
(`F1`…`F4` в сообщениях — это порядок работы, а не пункты F1–F8).
