# ADR-0012: Единый справочник ступеней кю/дан как источник истины

- **Статус:** предложено
- **Дата:** 2026-10-25
- **Связано:** BR-015 (справочник поясов), #30–#32, Issue #30

## Контекст

Сейчас пояс и ступень — два независимых поля:

- `Athlete.beltGrade` — пояс спортсмена (`BeltGrade`, 12 значений);
- `Certification.stageKind` + `stageNumber` — кю/дан аттестации.

Их можно сохранить в противоречивом сочетании: «синий пояс, 10 кю», «чёрный пояс, 3 кю». Ни API, ни админка такую пару не запрещают. В киокушине ступень однозначно определяет пояс, поэтому противоречие — не «неаккуратные данные», а ошибка модели.

Кроме того, 0 кю (белый пояс без экзамена) нигде не выражен: белый пояс существует как значение `beltGrade`, но не как ступень.

## Решение

Ввести `RankCatalog` в `packages/contracts` — фиксированный справочник ступеней. Ступень становится источником истины, пояс выводится из неё.

1. **Модель.** Ступень `Rank` — это пара «вид + номер»: `KYU 0…10` или `DAN 1…10`. Идентификатор `kyu-0`, `dan-1` стабилен и попадает в БД.
2. **Пояс.** У каждой ступени ровно один пояс (цвет + полоска). Обратное неверно: чёрный пояс соответствует десяти ступеням (даны), поэтому «пояс → ступень» — не функция.
3. **Порядок.** Задаётся явно полем `order`: 0 кю = 0, 10 кю = 1, …, 1 кю = 10, 1 дан = 11, …, 10 дан = 20. Перестановка двух соседних записей — это другое правило, поэтому порядок не выводится из номера.
4. **Неизменяемость.** CRUD через админку запрещён: изменение набора — правка кода и ревью, как у `BELT_GRADES` (BR-015).
5. **Совместимость.** `beltGrade` остаётся в API на переходный период и вычисляется из ступени; писать его независимо нельзя. Это позволяет мобильному приложению и старым клиентам работать, пока они не перешли на `rank`.

## Последствия

**Плюсы:**
- противоречивые сочетания становятся невозможны на уровне модели;
- 0 кю выражен явно и является начальным состоянием;
- один источник для формы, карточки, истории и мобильного приложения.

**Минусы и риски:**
- нужна миграция существующих записей: старые данные могут содержать противоречия, и их нельзя разрешать угадыванием — нужен отчёт о неоднозначностях;
- два источника правды на переходный период (`rank` и `beltGrade`) — временно и только на чтение.

## Альтернативы

1. **Оставить два поля, валидировать в API.** Отклонено: валидация не спасает данные, записанные в обход API (миграции, seed, прямые правки), и не даёт 0 кю.
2. **Сделать справочник редактируемым.** Отклонено: клуб не меняет кю/даны, а редактируемый справочник ломает историю аттестаций.
3. **Хранить только пояс.** Отклонено: чёрный пояс не различает даны, а ступень — главный атрибут в киокушине.

## Приёмка

- новый спортсмен получает `kyu-0` и белый пояс;
- аттестация на 10 кю даёт оранжевый пояс;
- даны 1–10 имеют чёрный пояс и различаются номером;
- сохранить несовместимую пару «ступень/пояс» невозможно;
- после миграции исторические записи доступны, а неоднозначные вынесены в отчёт.
