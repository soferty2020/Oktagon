# ADR-0014: Приглашение по короткому коду

## Контекст

Доступ в систему выдаёт только администратор: самостоятельной регистрации нет
(ADR-0006, MVP scope). Механика была одна — приглашение по ссылке
`/invite/<token>`.

После выхода мобильного приложения выяснилось, что для тренера это неудобно:
ссылку надо открыть **в браузере**, задать пароль, потом поставить приложение и
войти. В зале, с телефона, это лишние шаги — и повод не пользоваться системой.

Deep link (универсальные ссылки) решает проблему, но требует домена, файлов
`apple-app-site-association` и `assetlinks.json`, а также настройки подписи
приложения. Это отдельная инфраструктурная работа, которую можно отложить.

## Решение

Приглашение получает **короткий код** из 8 символов. Суперадмин создаёт
приглашение в веб-админке и видит рядом со ссылкой код. Код передаётся
приглашённому любым каналом (мессенджер, голосом). В приложении на экране входа
есть «У меня есть код»: код, email, пароль, имя и фамилия.

### Код — то же приглашение, другой способ предъявить

Код не создаёт отдельную сущность: у `UserInvite` появляется `codeHash` рядом с
`tokenHash`. Срок, одноразовость и проверка email — общие. Принятие по коду
вызывает тот же `accept`, что и принятие по ссылке: правила не должны разъезжаться.

### Алфавит без похожих символов

`ABCDEFGHJKMNPQRSTUVWXYZ23456789` — без `0/O` и `1/I/L`. Код диктуют голосом и
переписывают из мессенджера; разница между `O` и `0` здесь стоит лишней попытки.

Ввод нормализуется: регистр, пробелы и дефисы не важны. Иначе человек с
телефона будет «вводить правильно» и получать отказ.

### Защита

Код короткий, поэтому:

- тот же лимит по IP, что у ссылки (`enforceInviteRateLimit`);
- в базе только хеш: по дампу нельзя восстановить действующий код;
- недействительный, истекший и использованный код неотличимы (`INVITE_INVALID`) —
  иначе перебором можно выяснить, какие приглашения существуют;
- код одноразовый: после успешного принятия приглашение погашено.

8 символов из 32 — около `32^8 ≈ 1.1·10^12` комбинаций. При лимите по IP
перебор бессмысленен.

### Роль приходит из приглашения

В приложении роль выбрать нельзя. Иначе любой, кто узнал код, выбрал бы себе
`SUPERADMIN` — а тренерский доступ означает данные детей.

## Последствия

- Тренер активирует доступ без браузера и deep link.
- Ссылка по-прежнему работает: в веб-админке она остаётся, и старые приглашения
  не ломаются.
- Код показывается **один раз**: повторно его не получить ни из списка, ни из БД.
  Потеряли — админ создаёт приглашение заново, предыдущее гасится.

## Альтернативы

**Deep link в приложение.** Правильнее для UX, но требует домена, файлов
ассоциации и подписи. Отложено: код решает задачу сегодня.

**Админ создаёт аккаунт с паролем.** Не требует изменений в приложении, но пароль
идёт по открытому каналу и его надо менять. Хуже.

**Автоматически по домену email (`@club.ru` → STAFF).** Отвергнуто: любой, кто
знает email тренера, зарегистрируется первым и получит доступ к данным детей.
Домен клуба не гарантирует принадлежность человека.

**Код на email.** Требует почтовой инфраструктуры, которой нет (docs/25).

## Приёмка

- Админ видит код при создании приглашения.
- Код принимается с любым регистром и с пробелами.
- Неверный код даёт `INVITE_INVALID`, повторный ввод использованного — тоже.
- После активации человек сразу попадает в интерфейс своей роли.
- Лимит по IP работает на обоих путях: код и ссылка.
