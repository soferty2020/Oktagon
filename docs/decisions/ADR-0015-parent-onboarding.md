# ADR-0015: Онбординг родителя — регистрация, код привязки и заявка

## Контекст

Доступ в систему выдавался только приглашением: администратор создаёт
приглашение, передаёт код или ссылку, человек активирует аккаунт. Для тренеров
это работает (ADR-0014), но для родителя создаёт тупик: скачал приложение,
увидел «попросите приглашение» — и ушёл.

Проблема не только в конверсии. Магазины приложений, в первую очередь App Store,
по guideline 4.2 требуют, чтобы приложение было полезно без внешнего ритуала.
Приложение, в которое нельзя войти без звонка администратору, под это требование
не подходит.

При этом самостоятельная регистрация не должна открывать данные детей: аккаунт
родителя сам по себе не даёт доступа к карточке ребёнка.

## Решение

### Аккаунт и ребёнок — разные вещи

Регистрация создаёт `User` с ролью `MEMBER` и статусом `ACTIVE`. Такой
пользователь видит общие разделы клуба — новости и расписание, но не видит ни
одного спортсмена. Связь появляется только через `UserAthlete`, и только двумя
способами ниже.

### Путь 1. Код привязки (быстрый)

Тренер или администратор в карточке спортсмена нажимает «Выдать код» и получает
8 символов. Родитель вводит код в приложении — связь создаётся сразу.

- Код одноразовый, живёт 72 часа.
- В базе только SHA-256 хеш: по дампу действующий код не восстановить.
- При выдаче нового кода предыдущие активные гасятся: забытый код из переписки
  не должен работать вечно.
- Алфавит без `0/O` и `1/I/L`: код диктуют голосом (тот же, что у приглашений,
  общий модуль `shared/link-code.ts`).
- Неверный, истёкший и использованный код дают один ответ `LINK_CODE_INVALID`:
  иначе перебором можно выяснить, какие коды существуют.

Кто может выдать: `athletes.edit`, а область — через `assertAthleteAccess`.
Тренер выдаёт код только по спортсменам своих групп; администратор — по любым.

### Путь 2. Заявка с подтверждением (когда кода нет)

Родитель заполняет ФИО ребёнка, дату рождения и телефон. Заявка попадает в
очередь администратора; тот видит кандидатов — карточки с похожей фамилией — и
подтверждает одну либо отклоняет с причиной.

Подтверждение создаёт `UserAthlete` и закрывает заявку. Отклонение сохраняет
причину: родитель видит её в приложении и может подать заявку заново.

Повторная заявка на того же ребёнка, пока предыдущая не рассмотрена, не
создаётся: иначе очередь заполняется дублями.

### Что видит родитель без детей

Новости клуба. Это осознанно: приложение должно быть полезным до привязки, иначе
оно снова «не работает без звонка». Расписание и остальные разделы требуют
привязки — там данные группы.

## Последствия

- Родитель начинает пользоваться приложением сам, без администратора.
- Тренер, у которого есть карточка ребёнка, решает быстрее администратора — код
  у него под рукой.
- Очередь заявок — работа для администратора, но только для тех, кто не получил
  код.
- Данные детей не открываются до подтверждения связи.

## Альтернативы

**Авто-привязка по email из карточки спортсмена.** Отвергнуто: почта ничем не
подтверждена, и любой, кто знает адрес родителя, получил бы доступ к данным
ребёнка. Это та же дыра, из-за которой в ADR-0014 отвергнута выдача роли по
домену.

**Только код, без заявок.** Быстрее в реализации, но если тренер недоступен или
карточка только заведена, родитель застревает. Заявка — страховка.

**Только заявки, без кода.** Каждая привязка идёт через администратора: при
50 родителях это 50 ручных решений.

## Приёмка

- Регистрация создаёт `MEMBER` и не даёт доступа к спортсменам.
- Код принимается с любым регистром и с пробелами.
- Истёкший, использованный и неверный код дают `LINK_CODE_INVALID`.
- Повторная привязка к тому же ребёнку — `LINK_CODE_ALREADY_LINKED`.
- Тренер не может выдать код по чужой группе.
- Заявка отклонённая и подтверждённая повторно не рассматривается.
- Все события — в аудите: выдача кода, привязка, создание и решение по заявке.
