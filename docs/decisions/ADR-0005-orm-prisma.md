# ADR-0005: Prisma как ORM и инструмент миграций

Status: Accepted

## Context

`docs/08-database.md` задает PostgreSQL, UUID-ключи, ограничения уникальности и
требование выполнять изменения схемы только миграциями. ORM спецификацией не
выбран. `docs/13-architecture.md` описывает модульный монолит на NestJS с
изоляцией внешних интеграций через adapters/interfaces.

Схема уже реализована в Prisma и применена к PostgreSQL 16.6: 28 таблиц,
13 enum-типов, миграция `20260101000000_init`. Это ADR фиксирует выбор и его
границы, чтобы решение не пришлось восстанавливать по коду.

## Decision

Использовать **Prisma** как ORM и инструмент миграций для backend.

Дополнительные решения, принятые вместе с основным:

1. **Сгенерированный клиент лежит внутри приложения.** В `schema.prisma` задан
   явный `output = "../generated/prisma"`. Причина: каталог `.prisma` в
   `node_modules` создается postinstall-скриптом пакета `@prisma/client`; если
   установка идет с `--ignore-scripts` (требование некоторых сред), клиент
   теряется. Явный `output` делает генерацию независимой от lifecycle-скриптов
   и одинаково работающей для `ts-node` и собранного `dist`.

2. **Доступ к БД только через `PrismaModule`.** Модули не создают собственные
   экземпляры `PrismaClient`: единственный экземпляр на приложение, транзакции
   передаются явно (см. `AuditService.record(event, tx)`).

3. **Ограничения, не выражаемые в Prisma, живут рядом с миграцией.** Два
   требования `docs/08-database.md` — не более одной активной `GroupMembership`
   и не более одного открытого `FreezePeriod` на спортсмена — реализованы
   частичными уникальными индексами PostgreSQL в
   `prisma/migrations/20260101000000_init/extra_constraints.sql`. Prisma schema
   их не описывает, поэтому файл обязан применяться вместе с `migration.sql`.

4. **Связь `GroupBranch` вместо `branchId` у группы.** ERD (`docs/22-erd.md`) не
   связывает группу с филиалом напрямую, а `docs/00-project-overview.md`
   говорит, что одна группа может заниматься в разных филиалах. Введена
   отдельная таблица связи. Это отклонение от ERD v1 и кандидат на обновление
   самой ERD.

5. **`AuditActor` без каскадного удаления.** `AuditLog.actorUserId` ссылается на
   `User` без `onDelete`, потому что аудит по BR-007 должен переживать удаление
   пользователя. Пользователи в MVP архивируются (`archivedAt`), а не удаляются
   физически.

## Consequences

Плюсы:

- типобезопасный доступ к данным и генерация типов из одной схемы;
- миграции воспроизводимы и хранятся в репозитории, что требует DoD;
- `prisma migrate diff --from-empty --to-schema-datamodel --script` позволяет
  получить SQL миграции без запуска schema-engine — полезно в средах, где
  запуск нативных бинарников запрещен.

Минусы и издержки:

- `prisma generate` становится обязательным шагом перед `typecheck` и `build`:
  сгенерированный клиент не хранится в git. Шаг зафиксирован в
  `docs/27-local-development.md`;
- для миграций нужен нативный `schema-engine`, который не запускается в
  некоторых ограниченных средах. Обход через `migrate diff` + psql описан в
  `docs/27-local-development.md`; в обычном окружении применяются штатные
  `prisma migrate dev` / `deploy`;
- часть бизнес-ограничений нельзя выразить в schema, поэтому нужно следить,
  чтобы `extra_constraints.sql` не потерялся при пересоздании миграции.

## Alternatives

- **TypeORM.** Ближе к «классическому» NestJS и умеет описывать часть
  ограничений декораторами, но миграции менее предсказуемы, а типы слабее
  выводятся из схемы. Отвергнут.
- **Kysely / Drizzle.** Дают больше контроля над SQL и легче переносятся, но
  требуют ручного описания типов и не дают готового инструмента миграций
  уровня Prisma Migrate. Отвергнуты как избыточные для MVP на 40 пользователей.
- **Сырой SQL без ORM.** Максимальный контроль, но высокая ручная работа на 28
  таблицах и отсутствие генерации типов. Отвергнут.
