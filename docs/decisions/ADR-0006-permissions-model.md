# ADR-0006: Модель прав доступа

Status: Accepted

## Context

`docs/04-roles-permissions.md` задает три базовые роли (MEMBER, STAFF,
SUPERADMIN), индивидуальные permissions поверх роли и ограничение scope для
STAFF. `docs/21-permission-matrix.md` уточняет, что проверяются **одновременно
capability и resource scope**: наличие permission не дает доступа к чужому
филиалу или группе. BR-010 запрещает доступ к финансам без явного permission.
BR-007 требует аудировать изменения прав.

Способ хранения и вычисления прав спецификацией не задан. От этого зависит
модуль identity (B1) и guards всех последующих модулей, поэтому решение нужно
зафиксировать до их реализации.

## Decision

Права вычисляются по формуле:

```
эффективные права = базовый набор роли ∪ индивидуальные UserPermission
доступ = есть permission AND ресурс попадает в scope
```

### 1. Базовый набор роли — в коде

`ROLE_PERMISSIONS` в `packages/contracts/src/domain.ts` сопоставляет роли набор
permissions из `docs/04-roles-permissions.md`. Набор меняется только через
изменение кода и ревью — не через БД.

### 2. Каталог permissions — в БД

Таблица `Permission` (`code`, `description`, `isFinancial`) заполняется seed-ом:
26 кодов из `docs/04-roles-permissions.md`, у финансовых выставлен
`isFinancial = true`. Каталог в БД нужен, чтобы админка могла показать список
прав и чтобы на `UserPermission` можно было поставить внешний ключ.

### 3. Индивидуальные выдачи — в БД

Таблица `UserPermission` (`userId`, `permissionId`, `grantedById`, `grantedAt`,
опциональный `expiresAt`). Индивидуальные выдачи только **добавляют** права
поверх роли; механизма «отозвать право роли у конкретного пользователя» в MVP
нет.

### 4. Resource scope — отдельное измерение

Scope не выражается permission'ом. В схеме есть `User.scopeAllGroups`
(по умолчанию `false`): STAFF без него видит только свои группы, с ним — все.
Роли MEMBER и SUPERADMIN в этом флаге не нуждаются: MEMBER ограничен своими
связанными спортсменами через `UserAthlete`, SUPERADMIN имеет полный доступ.

Правило проверки в guards:

1. SUPERADMIN — доступ разрешен;
2. permission отсутствует в эффективном наборе — 403 `FORBIDDEN`;
3. permission есть, но ресурс вне scope — 403 `FORBIDDEN` (не 404: скрывать
   существование ресурса не требуется, `docs/23-api-contract-plan.md` требует
   различать 401/403);
4. иначе — доступ разрешен.

### 5. Финансы защищены отдельно

Любой эндпоинт, читающий или меняющий финансовые данные, требует permission с
`isFinancial = true` (BR-010). Проверка выполняется на backend, а не в UI
(`docs/13-architecture.md`).

### 6. Изменения прав аудируются

Выдача и отзыв permission пишут `AuditAction.PERMISSION_GRANTED` /
`PERMISSION_REVOKED` через `AuditService` (BR-007).

## Consequences

Плюсы:

- базовый набор роли виден в ревью и не может быть незаметно изменен в БД;
- каталог в БД позволяет админке отображать права и ссылаться на них внешним
  ключом;
- scope вынесен из permissions: нельзя случайно выдать STAFF доступ ко всем
  группам, выдав ему одно право;
- единая точка вычисления эффективных прав упрощает тесты границ доступа
  (`docs/16-testing.md`, сценарий permission boundaries).

Минусы и издержки:

- смена базового набора роли — это деплой кода, а не правка данных. Для MVP с
  тремя ролями это приемлемо;
- scope в MVP булев (`scopeAllGroups`), а не список филиалов и групп. При росте
  до 5+ филиалов (`docs/00-project-overview.md`) понадобится отдельная таблица
  scope; это осознанное упрощение, а не финальная модель;
- `UserPermission` не умеет отзывать права роли. Если появится такая
  потребность, нужна отдельная таблица исключений и новый ADR.

## Alternatives

- **Полностью динамические роли в БД (`RolePermission`).** Гибче: новые роли без
  деплоя. Отвергнут для MVP: в спецификации всего три роли, а динамика добавила
  бы риск незаметного изменения прав в проде.
- **Только роли без индивидуальных permissions.** Проще, но `docs/04-roles-permissions.md`
  прямо требует индивидуальные права поверх роли, и `docs/21-permission-matrix.md`
  описывает их расширение для STAFF.
- **Permissions как claim-ы в JWT.** Убирает запрос к БД на каждый вызов, но
  отзыв права не действует до истечения токена. Отвергнуто: BR-007 и
  `docs/15-security.md` требуют серверных проверок, а отзыв прав должен
  применяться сразу.
