# ADR-0009: Модель расписания — шаблон, материализация и точечные изменения

- Статус: принято
- Дата: 2026-10-06
- Контекст: docs/22-erd.md, docs/01-mvp-scope.md, BR-009, docs/08-database.md,
  `packages/contracts/src/schedule.ts`

## Контекст

По MVP нужен квартальный регулярный график: «группа занимается по средам и
пятницам в 18:00». При этом отдельное занятие может быть перенесено, отменено
или проведено другим тренером — и это не должно переписывать график на весь
квартал (BR-009).

В схеме для этого уже есть две сущности: `ScheduleTemplate` со слотами
(`ScheduleTemplateSlot`) и материализованный экземпляр `TrainingSession` с
полями `changeReason`, `cancelledAt`, `status` и связью на шаблон.

## Решение

**Шаблон и экземпляр разделены и не выводятся друг из друга.** Шаблон отвечает
на вопрос «как группа занимается регулярно», занятие — «что происходит в
конкретный день». Экземпляры создаются материализацией (генерацией) на квартал.

**Экземпляр копирует ссылки, а не читает их через шаблон.** `hallId`,
`trainerProfileId` и `branchId` записываются в занятие при генерации. Поэтому
смена тренера в шаблоне на середину квартала не переписывает уже созданные
занятия: изменения вносятся точечно.

**Публикация фиксирует шаблон.** После `publishedAt` слоты менять нельзя:
расписание уже показано родителям, а занятия материализованы. Изменения
оформляются точечными правками занятий. Правка слота до публикации свободна.

**Материализация идемпотентна.** Уникальность `(groupId, startsAt)` уже есть в
схеме, поэтому повторная генерация не создает дублей. При `regenerate`
удаляются только занятия, которые еще не начались и не отменены вручную:
прошедшее занятие — это факт истории, его нельзя терять.

**Точечные изменения применяются к одному занятию** и требуют причины
(`changeReason`): перенос и отмена всегда объясняются, иначе родитель видит
изменение без повода (BR-007, аудит).

**Прошедшее занятие не редактируется.** Изменения по уже начавшемуся занятию
отклоняются (`SESSION_ALREADY_STARTED`): расписание — это история, а не только
план.

## Часовой пояс

Расписание задается локальным настенным временем клуба (`CLUB_TIMEZONE`), а в
БД хранится UTC. Перевод делается через `Intl`, а не через арифметику с
`Date.UTC`: иначе на смене летнего времени занятие сдвинется на час
относительно расписания. Расчёт вынесен в
`apps/api/src/modules/schedule/club-calendar.ts` и покрыт тестами, включая
переход на летнее время и занятия через полночь.

Квартал — календарное понятие: `year`, `quarter` (1..4) и границы `validFrom` /
`validTo` датами. Он не выводится из UTC-timestamps (docs/08-database.md).

## Последствия

- Материализацию нужно запускать явно (эндпоинт генерации): автоматическая
  генерация по расписанию потребовала бы фонового планировщика, которого в MVP
  нет.
- Правка слота после публикации запрещена, поэтому интерфейс обязан это
  показывать — иначе администратор будет искать способ изменить шаблон.
- Конфликты (зал занят, тренер занят, у группы уже есть занятие) проверяются на
  уровне сервиса: схема уникальность только по `(groupId, startsAt)`
  гарантирует.
- Занятия из шаблона и добавленные вручную не различаются в схеме. Признак
  `fromTemplate` вычисляется по наличию `scheduleTemplateId`; если понадобится
  различать ручные занятия отдельно, потребуется поле.
- Посещаемость (BR-008) опирается на материализованные занятия: без генерации
  отмечать посещаемость нечего, поэтому генерация идет до отметок в порядке
  работ.
