# ADR-0007: Граница identity-профиля и представление прав для клиентов

Status: Accepted

## Context

`docs/00-project-overview.md` требует, чтобы аккаунт не был равен карточке
спортсмена: один аккаунт может быть связан с несколькими спортсменами.
`docs/01-mvp-scope.md` включает в MVP одно Flutter-приложение для всех ролей,
`docs/23-api-contract-plan.md` — эндпоинт `GET /api/v1/me` и правило «DTO не
должны раскрывать финансовые поля неавторизованным ролям».

Форма ответа `GET /me` — публичный контракт: его будут читать `apps/mobile` и
`apps/admin`. После начала работы над клиентами изменение формы становится
ломающим. Решение нужно зафиксировать до реализации B1, потому что от него
зависит, какие данные собирает слой identity.

## Decision

### 1. `GET /me` отвечает только на вопрос «кто я»

Профиль содержит идентификацию, роль, статус и эффективные права. Связанные
спортсмены в него **не входят**: по MVP у аккаунта их может быть несколько, и
клиенту нужен отдельный список для переключателя. Отдельный эндпоинт
`GET /me/athletes` возвращает связанные карточки.

```json
{
  "id": "uuid",
  "email": "parent@example.com",
  "firstName": "Айгуль",
  "lastName": "Серик",
  "middleName": null,
  "phone": "+7...",
  "role": "MEMBER",
  "status": "ACTIVE",
  "scopeAllGroups": false,
  "permissions": {
    "codes": ["chat.use"],
    "grants": [
      { "code": "payments.view", "grantedAt": "2026-02-01T10:00:00.000Z" }
    ]
  }
}
```

### 2. Права отдаются двумя частями

- `codes` — итоговый набор, по которому клиент решает, показывать ли раздел;
- `grants` — только индивидуально выданные права с датой выдачи.

`grants` нужен админке, чтобы показать, что право выдано вручную, и дать его
отозвать. Разделение «право пришло от роли или выдано лично» не выводится из
`codes`, а без него экран управления правами неполон.

Клиент **не должен** использовать `codes` как единственную защиту: по
`docs/13-architecture.md` проверки выполняются на backend, а `codes` служат
только для управления интерфейсом.

### 3. Scope передается явно

`scopeAllGroups` едет в профиль отдельным полем. В MVP это булев флаг
(см. ADR-0006): STAFF без него видит только свои группы. Список конкретных
филиалов и групп в профиль не попадает — это вырастет в отдельный ресурс, когда
scope станет таблицей.

### 4. Секреты и внутренние поля не покидают backend

В ответ не входят: `passwordHash`, любые токены и их хеши, `createdAt`/`updatedAt`
служебных записей, содержимое `UserPermission.grantedById`. Контактные данные
спортсменов отдаются только пользователям с `athletes.contacts.view`
(`docs/15-security.md`, раздел Privacy).

### 5. Финансовые поля не попадают в профиль

`GET /me` не содержит сумм, задолженностей и статусов оплат, даже для
SUPERADMIN. Финансы живут в своих ресурсах под `payments.*` / `freezes.*`
(BR-010, `docs/23-api-contract-plan.md`).

### 6. Вычисление прав вынесено в чистую функцию

`resolvePermissions(user, rolePermissions, grants)` живет в
`packages/contracts` и не зависит от NestJS и Prisma. Причины: одна и та же
логика нужна backend-проверкам, тестам границ доступа и, потенциально, клиенту
для UI; чистую функцию проще покрыть тестами, чем сервис с БД.

### 7. Доступ к спортсмену проверяется отдельно от permissions

```
canAccessAthlete(actor, athleteId):
  SUPERADMIN            -> true
  MEMBER                -> есть связь в UserAthlete
  STAFF, scopeAllGroups -> true
  STAFF                 -> спортсмен состоит в группе тренера
```

Наличие `athletes.view` без попадания в scope доступа не дает
(`docs/21-permission-matrix.md`, раздел Enforcement).

## Consequences

Плюсы:

- форма профиля не зависит от количества связанных спортсменов — переключатель
  масштабируется без изменения контракта;
- разделение `codes` и `grants` закрывает экран управления правами, не раскрывая
  внутренние записи;
- чистая функция вычисления прав переиспользуется в тестах границ доступа
  (`docs/16-testing.md`, сценарии multi-athlete account и permission boundaries).

Минусы и издержки:

- клиенту нужны два запроса (`/me` и `/me/athletes`) вместо одного. Для MVP это
  дешевле, чем растущий ответ профиля;
- `grants` дублирует часть `codes`; при большом числе индивидуальных выдач ответ
  растет. В MVP число выдач измеряется единицами, риск несущественный;
- при переходе к таблице scope потребуется новое поле и версия контракта;
  текущий флаг придется оставить для совместимости или объявить breaking change.

## Alternatives

- **Один `GET /me` со связанными спортсменами внутри.** Меньше запросов у
  клиента, но ответ растет с числом спортсменов, а любой экран, которому нужен
  только профиль, тянет лишние данные. Отвергнут.
- **Отдавать права как claim-ы в JWT.** Убирает запрос за правами, но изменения
  прав не действуют до истечения токена. Отвергнут в ADR-0006 и здесь по той же
  причине.
- **Отдавать только `codes` без `grants`.** Проще, но админка не сможет отличить
  выданное вручную право от ролевого. Отвергнут.
