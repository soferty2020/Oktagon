# Security audit — первые результаты

- Дата: 2026-10-30
- Коммит: `e226b46` (main)
- Область: часть #49 (auth), #51 (web), #52 (сервер), косвенно #53 (бэкапы)
- Метод: чтение кода, конфигураций и проверка сервера по SSH. Без активных атак
  на production.

## Итог

Базовая гигиена в порядке: пароли — Argon2id с параметрами OWASP, refresh-токены
хранятся хешем и ротируются, cookies httpOnly + Secure + SameSite=Lax, CORS из
конфигурации, rate limit на входе и при приёме приглашений, секретов в git нет,
база и Redis не опубликованы наружу, файрвол и fail2ban включены, TLS действителен.

Найдено три замечания (одно среднее, одно низкое, одно про надёжность) и два
вопроса, которые нужно проверить отдельно.

## Находки

### S-1. Прокси админки не проверяет Origin (средняя, #51)

`apps/admin/src/app/api/proxy/[...path]/route.ts` пересылает `POST`, `PATCH`,
`PUT`, `DELETE` в API, подставляя токен из httpOnly-cookie, и не проверяет
`Origin`/`Referer` запроса. CSRF-токена нет.

Что защищает сейчас: `SameSite=Lax` — браузер не отправит cookie на cross-site
`POST`. Чего не хватает:

- `SameSite` защищает от *другого сайта*, но не от соседнего поддомена того же
  сайта (`*.octagon-karate.online`), если там появится что-то стороннее;
- `GET`-эндпоинты прокси доступны для cross-site навигации, и хотя они не меняют
  данные, они раскрывают содержимое в top-level переходе.

Рекомендация: в `forward()` для небезопасных методов сравнивать `Origin` с
`NEXT_PUBLIC_SITE_URL` (или заголовком `Host`) и отвечать `403` при несовпадении.
Оценка: ~20 строк + тест.

### S-2. Конфликт директив SSH — исправлено 30.10 (#52)

`sshd_config` и файлы в `sshd_config.d/` содержат одновременно:

```
PasswordAuthentication no
PasswordAuthentication yes
PermitRootLogin prohibit-password
PermitRootLogin yes
```

Фактическое значение сейчас безопасное (`sshd -T`: `passwordauthentication no`,
`permitrootlogin without-password`), но порядок чтения файлов решает исход:
достаточно, чтобы провайдерская панель или обновление переставило файлы, и вход
по паролю под root включится молча.

Рекомендация: оставить по одной директиве, убрать дубли из
`/etc/ssh/sshd_config.d/`, добавить проверку `sshd -T` в чек-лист деплоя.

### S-3. Восстановление из бэкапа — проверено 30.10 (#26 закрыт)

На сервере есть ежедневные зашифрованные дампы (`/srv/octagon/backups/*.dump.gpg`,
последний — 30.10 в 02:30). Это хорошая новость: бэкап существует и он не в
открытом виде.

Проверено 30.10 (#26 закрыт): дамп `octagon-20261030-0230` восстановлен в отдельную БД, 43 таблицы, `pg_restore` без ошибок; `athletes` 66/66, `groups` 16/16, `users` 6/6, `training_sessions` 142/142. Процедура — в `docs/14-infrastructure.md`.
восстановление не проверено, наличие файлов ничего не гарантирует: ключ, версия
PostgreSQL или порядок применения миграций могут оказаться несовместимыми.

Рекомендация: развернуть дамп в отдельную БД на сервере, сверить количество строк
по ключевым таблицам, зафиксировать процедуру в docs/14-infrastructure.md.

## #55: Flutter — токены, сеть, релизные ключи (2026-11-02)

| Что | Факт |
|---|---|
| Хранение токенов | `flutter_secure_storage` с `AndroidOptions(encryptedSharedPreferences: true)` — Keystore/Keychain, а не обычные prefs |
| Логирование токенов | в `api_client.dart` нет `print`/`debugPrint`; токен передаётся только в заголовке |
| Deep links | `intent-filter` только у launcher-активности, `exported` оправдан |
| iOS | `Info.plist` без `NSAllowsArbitraryLoads` — ATS по умолчанию включён |
| CI-сборка | `flutter build apk --release --dart-define=API_BASE_URL=https://api.octagon-karate.online/api/v1` |

### M-1. Release подписан debug-ключом (высокая для публикации)

`android/app/build.gradle.kts`: `signingConfig = signingConfigs.getByName("debug")` с
пометкой TODO. С debug-подписью APK нельзя публиковать в RuStore/Google Play, и
пользователь, установивший такую сборку, не сможет обновиться на релизную — подписи
не совпадут. Это же связывает #27 (приложение не опубликовано).

Рекомендация: создать release keystore (вне git), подключить через
`key.properties` (в `.gitignore`), включить `signingConfig = release`.

### M-2. `usesCleartextTraffic` в основном манифесте — исправлено 2026-11-02

`AndroidManifest.xml` разрешает HTTP для всего приложения. Комментарий объясняет
это локальным API, но в релизе это лишнее: при ошибке конфигурации трафик пойдёт
открытым текстом.

Рекомендация: убрать из `main`, оставить только в `debug`-манифесте (или
`network_security_config` с исключением для `10.0.2.2`).

### M-3. Дефолтный адрес API — исправлено 2026-11-02

`ApiConfig._defaultBaseUrl` рассчитан на эмулятор. Если релиз собрать без
`--dart-define=API_BASE_URL`, приложение молча пойдёт по HTTP на несуществующий
адрес. В CI флаг есть, в ручной сборке — нет.

Рекомендация: в release-режиме не подставлять дефолт, а падать с понятной
ошибкой конфигурации (`assert` или экран «сборка без адреса API»).

### M-4. Нет minify/shrink — исправлено 2026-11-02

`build.gradle.kts` не задаёт `isMinifyEnabled`/`isShrinkResources`: R8 не
обфусцирует код, строки и отладочная информация остаются в APK.

Рекомендация: включить `isMinifyEnabled = true`, `isShrinkResources = true`,
`proguard-rules.pro` для моделей.
## #56: персональные данные в логах и аудит-логи (2026-11-02)

## #53: PostgreSQL и Redis (2026-11-02)

Проверено на staging.

| Что | Факт |
|---|---|
| Пароли в `.env.staging` | `POSTGRES_PASSWORD` — 48 символов, `REDIS_PASSWORD` — 48, JWT-секреты — 64; дефолтных значений нет |
| Роль приложения | API ходит под **`octagon_app`**: `superuser=false`, `createdb=false`, `createrole=false` — правильный минимум |
| Миграции | отдельная роль `octagon` с правами суперюзера, приложению недоступна |
| Дампы | `/srv/octagon/backups` — `700 root`, файлы `600`, ключ `/root/.octagon-backup.key` |
| Сеть | 5432 и 6379 наружу не опубликованы (в `ss` только 22, 80, 443) |

### N-1. pg_hba с `trust` — исправлено 2026-11-02

`pg_hba.conf` в контейнере: `local all all trust`, `host all all 127.0.0.1/32 trust`.
Любой процесс, получивший доступ к сокету или localhost внутри контейнера БД,
входит под любой ролью без пароля. Внешнего доступа нет, но при компрометации
соседнего контейнера это снимает второй барьер.

Рекомендация: `scram-sha-256` для `host`-строк, `peer` для `local` (или `md5`),
перезапуск не требуется — только reload. Проверить после смены, что
`octagon_app` подключается по паролю.

### N-2. Redis protected-mode — исправлено 2026-11-02

`CONFIG GET bind` → `* -::*`: Redis принимает соединения на всех интерфейсах
контейнера. Порт наружу не открыт и `requirepass` задан, поэтому риск низкий.
**Исправлено:** `--protected-mode yes` добавлен в `docker-compose.staging.yml` (CONFIG REWRITE недоступен — сервер запущен без конфиг-файла). После перезапуска `CONFIG GET protected-mode` → `yes`; два неверных логина дают 401, rate limit работает.
## #50: RBAC и IDOR — первая проверка (2026-10-30)

Ядро доступа: `PermissionsGuard` (право) + `ResourceScopeService` (зона
видимости). Scope считается в контрактах `canAccessAthlete` / `canAccessGroup`:
SUPERADMIN — всё, STAFF — свои группы либо все при `scopeAllGroups`, MEMBER —
только связанные дети.

Живые проверки на staging (временный MEMBER и STAFF, после проверки заблокированы):

| Проверка | Результат |
|---|---|
| MEMBER → чужой спортсмен (`GET /athletes/:id`) | 403 |
| MEMBER → правка чужого (`PATCH /athletes/:id`) | 403 |
| MEMBER → чужая группа | 403 |
| MEMBER → список спортсменов | 403 |
| MEMBER → финансы, пользователи | 403 |
| STAFF → чужая группа | 403 |
| STAFF → чужой спортсмен | 403 |
| STAFF → список спортсменов | 200, **0 записей** (своих групп нет) |
| STAFF → финансы | 403 |

Контроллеры без `@RequirePermissions` проверены отдельно: `settings` и `audit`
закрыты `SuperadminGuard` по роли, `identity` — это `/me` под `AuthGuard`,
`news` — публичное чтение по BR-011, `chat` — доступ по участию (BR-012),
`trial-requests` — публичное создание заявки.

Продолжение проверки (2026-11-02):

- `competitions.get` ограничивает видимость: участник без своих детей получает 404 на чужой турнир;
- `competition-entries` вызывает `assertAthleteAccess` на каждой операции;
- `news` проверяет автора или право `news.edit.others`;
- `chat` проверяет участие в диалоге (FORBIDDEN для постороннего);
- `analytics` — пустая заготовка, наружу не отдаётся;
- `club-structure`, `trial-requests`, `settings`, `audit` — по правам или SuperadminGuard.

Наблюдение (не уязвимость, но функциональный разрыв): у STAFF нет `halls.view` —
`GET /halls` возвращает 403, хотя группы и тренеры открыты. Тренер без доступа к
справочнику залов может получить пустой экран в админке.

Не покрыто этой проверкой: маршруты записей и онбординга
и чата по всем id; права внутри `finance` (видны ли чужие суммы при наличии
`payments.view`); XSS в админке.
