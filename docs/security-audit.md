## Находки

### S-1. Прокси админки не проверяет Origin (средняя, #51)

`apps/admin/src/app/api/proxy/[...path]/route.ts` пересылает `POST`, `PATCH`,
`PUT`, `DELETE` в API, подставляя токен из httpOnly-cookie, и не проверяет
`Origin`/`Referer` запроса. CSRF-токена нет.

Что защищает сейчас: `SameSite=Lax` — браузер не отправит cookie на cross-site
`POST`. Чего не хватает:

- `SameSite` защищает от *другого сайта*, но не от соседнего поддомена того же
  сайта (`*.octagon-karate.online`), если там появится что-то стороннее;
- `GET`-эндпоинты прокси доступны для cross-site навигации, и хотя они не меняют
  данные, они раскрывают содержимое в top-level переходе.

Рекомендация: в `forward()` для небезопасных методов сравнивать `Origin` с
`NEXT_PUBLIC_SITE_URL` (или заголовком `Host`) и отвечать `403` при несовпадении.
Оценка: ~20 строк + тест.

### S-2. Конфликт директив SSH — исправлено 30.10 (#52)

`sshd_config` и файлы в `sshd_config.d/` содержат одновременно:

```
PasswordAuthentication no
PasswordAuthentication yes
PermitRootLogin prohibit-password
PermitRootLogin yes
```

Фактическое значение сейчас безопасное (`sshd -T`: `passwordauthentication no`,
`permitrootlogin without-password`), но порядок чтения файлов решает исход:
достаточно, чтобы провайдерская панель или обновление переставило файлы, и вход
по паролю под root включится молча.

Рекомендация: оставить по одной директиве, убрать дубли из
`/etc/ssh/sshd_config.d/`, добавить проверку `sshd -T` в чек-лист деплоя.

### S-3. Восстановление из бэкапа — проверено 30.10 (#26 закрыт)

На сервере есть ежедневные зашифрованные дампы (`/srv/octagon/backups/*.dump.gpg`,
последний — 30.10 в 02:30). Это хорошая новость: бэкап существует и он не в
открытом виде.

Проверено 30.10 (#26 закрыт): дамп `octagon-20261030-0230` восстановлен в отдельную БД, 43 таблицы, `pg_restore` без ошибок; `athletes` 66/66, `groups` 16/16, `users` 6/6, `training_sessions` 142/142. Процедура — в `docs/14-infrastructure.md`.
восстановление не проверено, наличие файлов ничего не гарантирует: ключ, версия
PostgreSQL или порядок применения миграций могут оказаться несовместимыми.

Рекомендация: развернуть дамп в отдельную БД на сервере, сверить количество строк
по ключевым таблицам, зафиксировать процедуру в docs/14-infrastructure.md.

## Что проверено и в порядке

| Область | Факт |
|---|---|
| Пароли | `@node-rs/argon2`, `memoryCost 19456`, `timeCost 2`, `parallelism 1` (OWASP для 2 vCPU) |
| Refresh-токены | в БД хранится SHA-256, есть TTL и ротация |
| Rate limit | `RateLimiterService` на Redis; применяется на `POST /auth/login` (по IP) и при приёме приглашения |
| Приглашения | поиск **только по токену или хешу кода**, email сверяется, истёкшие и использованные неотличимы от неверных |
| Cookies админки | `httpOnly: true`, `sameSite: 'lax'`, `secure` в production, `path: '/'` |
| CORS | источники из `CORS_ORIGINS`, `credentials: true`, без `origin: true` |
| Секреты | в git только `.env.example`; рабочих ключей в репозитории нет |
| Сервер | UFW active (22/80/443), fail2ban active, TLS Let's Encrypt до 22.01.2027 |
| Порты | наружу слушают только 22, 80, 443; PostgreSQL и Redis не опубликованы |
