# 26. Admin Settings — утверждённые требования

Status: Approved product decisions (2026-10-23). Технические варианты ниже являются предложением к реализации, если не помечены как утверждённые.

## Решения
1. Роли сотрудников: **готовые роли + индивидуальные права**. Создание произвольных ролей в MVP не требуется.
2. Пояса: **фиксированный справочник**. Добавление/удаление/редактирование набора поясов через UI запрещено; отображение текущего пояса спортсмена сохраняется.
3. Филиалы: **только общие параметры и адреса**. Отдельные конфигурационные правила для филиалов не нужны. Операционный CRUD филиалов и залов остаётся в соответствующем разделе.
4. Финансы: **суперадмин может менять правила расчёта задолженности**. Конкретные доступные параметры и варианты ещё требуют согласования, нельзя заменять действующий BR-004 без спецификации и тестов.
5. Журнал действий: **доступ только суперадмину**. Право просмотра аудита не делегируется через индивидуальные права в MVP.
6. Системные настройки: **только безопасные параметры через админку**. Секреты, инфраструктура, бэкапы, миграции, провайдеры, переменные окружения — вне UI.

## Информационная архитектура
- Общие сведения клуба: название, логотип, контакты, часовой пояс (изменение timezone — отдельная проверяемая операция).
- Филиалы: ссылка в операционный справочник; название, адрес, контакты, активность.
- Сотрудники и права: ссылки на существующие экраны; роли MEMBER/STAFF/SUPERADMIN, индивидуальные grants и resource scopes.
- Спортивные справочники: read-only каталог поясов; редактирование текущего пояса — в карточке спортсмена при наличии права.
- Финансовые правила: отдельный экран суперадмина с версионируемой конфигурацией задолженности.
- Расписание: отображение правил планирования, ссылки на существующие шаблоны и исключения; новые глобальные правила — только после согласования.
- Коммуникации: настройки видимости/доступа в рамках существующих permissions; никаких push в MVP.
- Журнал действий: только суперадмин, фильтры по времени, актору, сущности и действию, просмотр before/after; без редактирования/удаления.
- Система: безопасные общие параметры, без управления инфраструктурой.

## Финансовые настройки: важная граница
Текущий BR-004 является действующим правилом до утверждения нового набора параметров. Необходимо определить:
- какие именно условия долга доступны для изменения;
- применяются ли новые настройки только к будущим месяцам или ретроспективно;
- как обрабатываются частичная оплата, expectedAmount и полная оплата;
- что происходит при заморозке и изменении расписания задним числом.

Рекомендуется хранить версии конфигурации с effective_from и журналом изменений. Должна быть preview-оценка влияния на список должников до сохранения, подтверждение и тесты перехода версий. Это рекомендация, не утверждённое поведение.

## Backend security
- GET/PATCH общих настроек: только явно авторизованные пользователи.
- Финансовые правила: чтение/изменение только SUPERADMIN.
- Audit log: чтение только SUPERADMIN независимо от индивидуальных grants.
- Изменение permission grants не может повысить привилегии сверх допустимого scope.
- Системные секреты не сериализуются в API и не доступны UI.
- Все изменения настроек аудируются, включая старое и новое значение.

## Acceptance criteria
- STAFF не может читать журнал действий даже с произвольными индивидуальными правами.
- STAFF не может менять финансовые правила.
- Изменение финансового правила не допускается без валидации и аудита.
- Нельзя менять фиксированный справочник поясов через admin API.
- Сотрудник с соответствующим разрешением управляет филиалами только в разрешённом scope.
- Секреты и параметры инфраструктуры не возвращаются через endpoints настроек.
- Изменения общих сведений клуба сохраняются и корректно отображаются после повторного входа.
- Принятые решения не ломают текущие сценарии BR-004 и действующий финансовый API.

## Dependencies
Существующие auth, permissions, club structure, finance, audit, admin UI. Реализацию финансовых переключателей блокирует уточнение семантики правил долга.
